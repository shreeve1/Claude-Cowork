# Claude Cowork setup

For the owner’s agent. This product supports Claude Cowork only. The attached Release is a maintainer distribution, not the folder tree to copy into a user workspace.

## Guide the owner at every step

This applies to every step of fresh setup, migration and updates, including adaptation and recovery. The agent handles routine extraction, file selection, paths, copying and checks. When the owner must act, explain the purpose in one sentence, give a short numbered sequence of clicks or a specific reply, then say what happens next. Give only the next needed action and verify the result before continuing. Keep the owner oriented and the work moving: show the Roadmap below at the start, name the current stage when it changes, and, once the owner’s reply confirms an approval or click, continue to the next stage in that same turn. A turn that needs the owner ends with that one request as its `Next:`; every other turn ends with `Next:` and the coming step. Combine the decisions that are ready into one message the owner can answer in one reply, rather than one turn per item. Ask about the owner’s work and preferences, real conflicts and required approvals, not technical implementation choices.

Use the controls actually visible in the owner’s Cowork version. **Add folder** was visible below the message box in the Windows test; **Choose folder** may appear when opening the picker. If labels differ, identify the matching control or ask for a screenshot of that area. Never invent a button, claim a click happened or bypass an organization restriction.

- **Attach the ZIP:** “Add the downloaded ZIP to this conversation using the attachment control, then send it. You do not need to extract it yourself; I will read the setup instructions inside it.” Verify that the attachment is readable before proceeding.
- **Fresh workspace:** “In File Explorer, open **Documents**, click **New → Folder**, and name it **Cowork Workspace** or a name you prefer. Back in Cowork, click **Add folder**, then **Choose folder** if offered, select the empty folder you just created and confirm.” Explain that this is the new working folder. Check it is empty before creating files; preserve a nonempty folder and guide selection of a different empty destination.
- **Migration access:** “Click **Add folder**, choose your existing setup folder and confirm. Repeat for the new empty workspace folder. Tell me which is the original and which is the destination.” Explain that the original stays untouched, then verify both roles and paths. Summarize what will be brought across, what stays behind and where it goes; request approval of that specific plan before migrating content.
- **Update access:** “Click **Add folder**, choose the workspace you already use and confirm. I will update that same folder, not create a replacement.” Verify the selected workspace before planning changes.
- **Backup access and approval:** Recommend a persistent backup subfolder under Documents only after checking suitability. If access is needed, say: “To keep a lasting safety copy, click **Add folder**, then **Choose folder** if offered. Select **Documents** and confirm. This gives access for the backup; your working folder stays unchanged.” Resolve the actual Documents path, check it is outside the workspace and extracted Release, and show the full proposed backup path. Ask: “May I create and verify your backup at `[full path]` before updating `[workspace]`?” Folder access alone is not backup-location approval. The agent creates the dated backup subfolder after confirmation; the owner need not create it. If Documents is unavailable or unsuitable, recommend one specific safe persistent alternative and explain how to select it. Never offer session-only scratch storage as the normal backup route; no suitable persistent location means stop before workspace changes.
- **Skills:** Explain that ready-made cards install capabilities into Cowork; follow the concrete **Save skill** instructions below. Present the next batch only after the previous one is confirmed and checked. Ask separately about optional video skills.
- **Personalization and conflicts:** Recommend a layout from the owner’s actual work and explain the result in plain language. Ask only questions whose answers change it. For a conflict or removal, name the affected item, what would change and what will be preserved; request that specific approval separately from backup or installation. Translate technical-only differences into a short result rather than individual file questions.
- **Checks, blockers and finish:** Run checks yourself and report what passed. If the owner must resolve a blocker, identify the exact next click or information needed and the operation waiting for it. At completion, state the working folder, backup location when applicable, confirmed installs, anything pending and a concrete first action such as “Keep this folder attached and ask me to create a task.” Offer rollback only with its separate approval and preservation checks below.

**Roadmap.** Show the owner the stages for their situation in plain words:

- **Fresh setup or migration:** create your workspace; install the two memory skills; settle how your work is organized (migration: approve the plan for your old material); learn your tools; practice on real work; install the remaining skills that fit; wrap up.
- **Update:** back up; review what changed; apply approved changes; install changed skills; check; what's new for you.

## Getting the source

For first setup, migration and updates, the owner downloads the ZIP from `https://github.com/shreeve1/Claude-Cowork`, adds it to the conversation and pastes prompt 1, 2 or 3 from its README. Use that attachment; do not fetch or clone GitHub.

Extract into separate staging, never over an existing workspace. Reject absolute paths, parent traversal and links escaping staging. Locate the repo root inside the ZIP. Use one extracted copy throughout and record its ZIP identity and Release. Missing or unreadable files block setup: ask for a complete attachment or access to a separately extracted copy, not a network workaround.

## What belongs where

- **Maintainer Release:** `.claude/skills/` source, persona libraries, `.claude/setup/`, build/conversion scripts, tests and ready-made `.skill` files. Read these in staging when setup needs them. Never copy the source tree, persona files, builders, tests or package archives into a fresh user workspace.
`START-HERE.md` and `memory/preferences/cowork-environment.md` in the Release are agent reference material only. Do not copy or recreate them in new or migrated workspaces, including during approved content migration. Keep old originals untouched and preserve existing owner files unless their separate removal is explicitly approved. The helper supplies user-specific rules/index without references to that note; installed-skill discovery stays in the user `CLAUDE.md`.

- **Cowork installation:** show ready-made `.skill` cards from staging with `present_files`; the owner clicks **Save skill**. Do not build, zip, unpack into the workspace or treat source-file copies as installation (except owner-approved project skills, below).
- **User workspace:** the filtered files selected by staged `.claude/cowork/workspace.py`: Cowork-specific `CLAUDE.md`, memory structure and preferences, saved tasks, project scaffolding, standalone Git hooks and the package index for later comparisons. The projected `MANIFEST.json` describes only these files. `memory/README.md` comes from personal-memory’s project scaffold, not the maintainer memory guide.

Owner-added files and skills in an existing workspace stay put. A legacy `.claude/skills/` tree is not permission to delete anything. Identify and preserve custom skills; offer optional cleanup of confirmed shipped sources only after setup works and the owner explicitly approves removal. Never ask about individual unchanged persona files.

## First setup

Use this for a fresh owner workspace or migration from another setup. The old setup stays read-only. Follow "Guide the owner at every step" throughout, including folder access, installation, personalization, approvals and completion.

1. **Create the user workspace.** Read the changelog, explain this workspace in two or three lines and show the Roadmap. With Python, run the staged helper: `python3 "<Release>/.claude/cowork/workspace.py" create "<Release>" "<new empty workspace>"`. It refuses nonempty destinations and source overlap. Without Python, follow the same file-selection and override rules in that helper using file tools; verify the copied files and projected manifest manually. Do not copy the entire Release. Do not add nonexistent projects or facts.
2. **Install the first-stage skills.** Present the first-stage cards in "Skills in Cowork" below and verify that they are installed, with personal-memory and memory-setup and their needed files are readable before using them. Setup may read staged instructions to explain/install the packages, but daily work must resolve the installed package, not keep staging as a runtime dependency.
3. **Set up memory and tasks.** Follow installed memory-setup, with the old setup as source or none. Use its tracking-model instructions to settle the owner’s work, useful project folders, memory subjects and procedure topics. Preserve existing notes, task IDs, archives and pending proposals. Show the migration plan with every group in one message, so the owner can approve, change or decline each group in one reply; write no migrated content before that approval. Use the installed personal-memory templates and recovery helpers. A missing task index is created only at approved setup or task creation; restore existing unfinished rows rather than resetting them.
4. **Adapt, practice and verify.** Follow staged `ADAPTING.md` through every section, including the owner’s environment and practice on real work. Verify the owner’s actual project/file links and memory/task structure. Run installed personal-memory’s helpers and audit, or its disclosed manual checks if permitted. Incomplete legacy procedures need owner-assisted repair and real verification; never invent dates or delete notes to clear an audit. Confirm that no maintainer source, package archives, `START-HERE.md` or shipped Cowork environment preference were copied or recreated. Preserve existing owner files with those names.
5. **Install the remaining skills.** Present the second-stage cards in "Skills in Cowork" and confirm each batch before the next.
6. **Suggest rules.** From the practice runs and the owner’s real work, suggest at most seven useful preferences with reasons and destinations. Ask which they want, save only approved rules through installed personal-memory, and audit again. With little evidence, ask what they use the agent for or skip. Never put personal rules into shipped instructions.
7. **Offer project import.** After adaptation, offer to bring the owner’s Claude app Projects into the workspace, run by the installed `project-import` skill’s import (one project per chat). Skip this when they have none or decline.
8. **Finish.** Report what moved, what stayed behind, practice runs done or saved for later, installed versus merely presented cards, checks run and limitations. The setup folder stays in staging, so there is no user setup-folder deletion step. Commit only this session’s changes if Git is available; preserve unrelated staged work.

## Skills in Cowork

First setup installs in two stages. First stage, one batch: `personal-memory.skill`, `memory-setup.skill` and every other skill a `skill` pointer in the workspace’s `memory/rules.md` names, from staged `.claude/cowork/skills/core/` with `present_files`. Memory setup needs the first two, and its audit fails while a skill named in the rules is missing. Second stage, after practice: present the remaining core cards in bounded batches, first those that fit work the owner described, each with one line on what it does for them, then the rest as one optional batch. When a chosen practice run needs a card not yet installed, present it then, wait for the owner to confirm **Save skill**, verify access, and only then start the run. Ask separately whether they also want optional video skills; show staged `video/*.skill` only on yes. Do not create a Cowork environment preference to record this. Report the confirmed selection and retain the package index; capture only an owner-specific durable preference in an appropriate existing note under personal-memory recovery.

For each batch, say: “Click **Save skill** on each of these cards, then tell me when you have finished.” Explain that this installs the skills into Cowork, not the workspace folder. Verify access before presenting the next batch; a displayed card is not a confirmed installation. The owner clicks **Save skill** on each card. A card without that button may mean the organization forbids adding skills: explain that they need their admin, and report installation blocked rather than claiming success. Do not try to bypass the restriction. Keep owner-created installed skills untouched. Owner-approved project skills are the one thing you build: create each per the installed `project-import` skill’s `project-skills.md` and install it with **Save skill**. The how-to stays in that skill.

For an update, compare against the verified pre-update backup: `python3 "<Release>/.claude/cowork/cowork_skills.py" changed "<backup folder>" --workspace "<Release>"` (add `--video` only if selected). Run from staging; no workspace skill-source tree is needed. Show only listed new/changed packages. Explain `removed`, `moved to video` and legacy-loader notices; the owner manages removals in Cowork settings. With no prior package index or video answer, ask and present the selected sets as first-time installation. Without Python, compare the staged and backup package indexes manually, reporting the limitation.

Resolve personal-memory from its actual Cowork installation for the current session. Verify `SKILL.md`, `tasks.md`, adjacent templates, needed scaffold files and scripts; never assume `/home/james/...`, `~/.claude/skills` or any other app’s install layout. If access is missing, stop affected work and explain what is needed. Installed personal-memory documents the allowed manual checks; unavailable recovery or safe containment still blocks writes.

## Git and Python

Both are optional; check them yourself only when needed and never install tools without approval. Explain Git as local version history and Python as support for automated checks. Recommend the supported route available in this session; keep commands and helper-path discovery with the agent rather than asking the owner to choose a technical method. Python in Cowork’s sandbox is `python3` (3.10+).

With Git and Python, offer a local repository and `.githooks` configuration. After verifying the installed personal-memory helper folder, set `git config --local cowork.personalMemoryPath "<installed personal-memory folder>"` and `git config core.hooksPath .githooks`. This machine-local helper path may change between sessions: recheck it when needed. The standalone hook scans staged secrets and audits memory through the installed helper; a missing required helper fails explicitly. Do not copy skill sources to satisfy the hook or bypass it. Without Python, use `.githooks/nopython` for message length only, and disclose that automated secret/memory checks are off.

Preserve all unrelated staged/uncommitted files. A Git lock does not prevent a file backup: verify whether it belongs to a live process before proposing removal, and obtain permission. Never commit owner documents or delete a lock just to prepare an update. If an unrelated Git blocker prevents a commit, report it without bypassing hooks.

## A newer version arrived

Update the existing workspace in place; keep the same user folder. Do not run First setup over it. Follow "Guide the owner at every step" throughout; a backup-access request must explain that it does not select a new workspace.

1. **Stage and identify.** Extract the attached ZIP as above. Read the current Release and newer changelog sections. Run staged `workspace.py plan "<Release>"` to obtain the projected user manifest and each file’s staging source. Compare only projected user files, not the full maintainer manifest. Normalize CRLF to LF for text hashes, as the manifest specifies; line-ending-only changes are not personal edits or individual approval decisions. For legacy workspaces, compare against their installed manifest for ownership, but never import the old source tree into the new projected manifest. Missing ownership evidence means ask before replacement.
2. **Back up before decisions about replacement.** Recommend a concrete persistent backup location, normally `Documents/Cowork Backups/<workspace name>/<unique timestamp>`, after checking that it is outside the workspace and staging. Follow the backup folder-access wording above. Confirm the location, then create and verify a unique complete backup outside the workspace/staging, including hidden files, `.git`, uncommitted work and both recovery folders. Compare inventory, bytes and required metadata; changed/unreadable files stop the copy. Keep it access-restricted, unchanged and outside recall. Ignore rules are not encryption. No user-workspace changes before verification. Do not bundle this approval with optional videos, instruction replacement or removals.
3. **Plan and check.** Show real owner-content conflicts and proposed removals, grouped in plain language. Preserve owner notes, rules, glossary, `CONTEXT.md`, schema choices, folder map, personal skills, documents, task IDs/history/archive and proposals. Before editing handwritten memory/tasks apply their separate installed recovery protocols; the full backup does not replace them. For edited `CLAUDE.md`, propose preserving owner adaptations in memory and using the projected Cowork instructions, with approval. Check legacy procedures with the new personal-memory helper from staging or its manual checks before replacement; unavailable repairs stop the update. Staged helpers are allowed for this compatibility check only, not as a lasting workspace dependency.
4. **Apply only approved user-file changes.** Use the projected manifest’s `source` paths. Add/replace approved shared user files and standalone hooks, preserving starter/owner files. Reconcile `memory/schema.json` without resetting owner choices; propose optional new topics. Do not add `START-HERE.md` or the shipped Cowork environment preference. Preserve any existing owner versions and useful owner adaptations; exclusion from the new projection never authorizes deletion. Never overwrite owner folders wholesale. No copying `.claude/skills/`, persona libraries, `.skill` archives, setup or maintainer scripts. Retired/legacy sources require separate explicit removal approval; preserve custom skills even if names overlap shipped skills. Keep `.git`, remotes and recovery intact.
5. **Install changed cards.** Follow "Skills in Cowork" against the backup, using the staged packages. Verify the installed personal-memory package again, recheck the hook’s machine-local helper path, and reconcile task startup via installed memory-setup step 3b only with approval. Keep existing task records and routing. Switch the “Starting or continuing work on a project” rules row to lead with skill `project-import` only after the `project-import` card is confirmed installed; if it is declined or blocked, keep the previous row (load the folder map, open the README). Update the workspace’s package index only after selected card installs are confirmed; if incomplete, retain the previous index and report the pending cards rather than calling the update complete.
6. **Verify and finish.** Run installed personal-memory indexes/hubs when needed, audit memory, verify task/project links and protected content against the backup except approved changes, and verify approved shared files against the projected manifest. Save the projected manifest without staging-only `source` fields as the workspace’s new manifest only after successful verification. Preserve owner `START-HERE.md` unless a merge is approved. Commit only this session’s changes, never unrelated staged files or a push. Report the same workspace path, backup, limitations and anything pending. A failed write/check stops the update; offer recovery, not blind continuation. Keep the backup.
7. **Show what's new for the owner.** After verification passes, explain the changes that affect work the owner actually does, one plain line each with an example phrase to try; summarize internal changes in one line, or say nothing changed for their work. Ask whether their work has changed since setup; if it has, revisit organization through `ADAPTING.md` section 2 with approval. When a change affects their work, offer one practice run with it.

### Older Releases

Skipping Releases is allowed; read every intervening changelog section. Missing `memory/rules.md` needs approved routing for existing owner rules, not a reset. Preserve task records and restore active/waiting index rows only through installed personal-memory’s task protocol. Preserve old `memory/log.md`, superseded notes and retired tools in the verified backup; propose cleanup with approval, never delete to clear an audit. Check approved procedures for real risk/approval/verification metadata; unresolved gaps stop affected execution. Confirmed obsolete hooks or sources may be removed only after approval, without discarding custom files. Existing remotes stay unchanged; a push needs current approval.

## Controlled update helper (experimental)

Read `UPDATE-RECOVERY.md` to enforce an exact approved file plan and retain restartable content recovery. This supplements the complete-backup requirement above; it does not yet replace it. Ordinary attached-ZIP update acceptance is still required before changing the default. Use read-only inspection first; no manifest entry or command flag substitutes for owner approval.

## Going back

The verified pre-update backup is the way back. Before restoring, identify later work, agree what to preserve, obtain explicit approval and verify a separate copy of the current state. Restore only the approved files/snapshot, then check content, task/memory consistency and installed skill compatibility. Restoring workspace files does not undo Cowork Save skill changes; explain those separately. Keep both backups and never automatically delete newer work or reset Git destructively. A migration can return to its untouched old setup.
